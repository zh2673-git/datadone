# DataDone-RE 项目现状与本质反推

> 本文档按「本质工坊」场景 D（项目解析）的逆向三阶流程生成，用于在引入 AI 分析功能前，先对现有系统进行本质定位。
> 思考层流程：实现观察 → 设计推导 → 本质反推。

---

## 一、项目概览

**项目名称**：DataDone-RE 多源数据分析系统  
**当前版本**：v1.0.2  
**核心用途**：面向纪检监察等调查场景，自动处理银行账单、微信账单、支付宝账单、话单四类数据，生成结构化 Excel 详表 + Word 解读式分析报告。  
**技术栈**：Python ≥ 3.10、Pandas、Pydantic V2、openpyxl、python-docx。  
**架构方法**：基于「数据规矩 → 数据存储 → 数据流转 → 接口层」四层架构，通过「本质探索」方法论正向推导而来。

---

## 二、实现观察

### 2.1 目录与模块组织

项目已具备清晰的分层：

```
datadone-re/
├── main.py                 # CLI 入口
├── src/
│   ├── application.py      # 应用协调器（全局状态 + 模块编排）
│   ├── config/             # 配置管理（settings / keywords / thresholds）
│   ├── datasource/         # 数据加载（bank / wechat / alipay / call）
│   ├── analysis/           # 分析引擎（11 步分析器）
│   ├── models/             # Pydantic 数据规矩
│   ├── export/             # 报告导出（Excel / Word）
│   ├── interface/          # CLI 交互
│   └── utils/              # 工具函数
└── docs/re-docs/           # 已有四层设计文档
```

### 2.2 分析引擎的 11 步流程

`src/analysis/engine.py` 按固定顺序编排：

1. 存取现识别
2. 频率分析
3. 特殊分析（特殊金额 / 特殊日期）
4. 综合交叉分析
5. 重点收支识别
6. 大额资金追踪
7. 高级分析
8. 行为基线
9. 基于基线的异常检测
10. 行为模式识别
11. 时序链分析
12. 风险研判
13. 习惯兴趣识别

### 2.3 数据模型与全局状态

- 所有分析结果统一封装在 `AnalysisResult`（Pydantic BaseModel）中。
- `Application._state` 是全局单一状态源，模块通过接口契约读写，禁止直接操作他模块内部状态。
- 原始数据用 `pd.DataFrame`，规矩层用 Pydantic，两者之间有明确的转换边界。

### 2.4 输出形态

- **Excel**：11 个工作表，涵盖汇总、明细、频率、交叉、异常、模式、风险、习惯等维度。
- **Word**：解读式报告，遵循「解读而非报数，聚合而非罗列，指向而非复述」原则。

### 2.5 实现洞察（视角升级）

> 现有系统不是在做「通用数据分析」，而是在一个强约束场景下做「证据信号的流水线生产」：输入被严格限定为四类本地数据，输出被严格限定为可审计、可回溯、可解释的调查线索。
>
> 这一实现选择意味着：**系统把「可解释性」和「确定性」放在比「发现能力」更高的位置**。任何新增能力（包括 AI）如果破坏了这个优先级，都会与现有架构气质冲突。

## 三、设计推导

### 3.1 反推因果链

| 观察到的设计选择 | 反推原因 | 与本质的关系 |
|---|---|---|
| 仅支持四类数据源 | 调查场景下可获取的数据类型有限，系统必须在约束内求解 | 约束即设计起点 |
| 使用 Pydantic 定义全部结果模型 | 调查结论需要被审计、被质疑，必须有类型级的数据规矩 | 可解释性需要结构保障 |
| 分析引擎按固定顺序执行 | 后续分析依赖前置结果（如异常依赖基线、模式依赖异常） | 流水线式证据生产 |
| 输出 Excel + Word 两种格式 | Excel 用于「查」，Word 用于「读」 | 同一证据信号的两种消费场景 |
| 不引入外部数据库 / 网络服务 | 数据敏感，必须本地化运行 | 安全与合规约束 |
| 无 LLM 依赖 | 避免不可解释、不可审计的「黑箱结论」 | 确定性优先于智能 |

### 3.2 技术选型分析

| 技术点 | 选择 | 推导逻辑 |
|---|---|---|
| 语言 | Python | 数据科学生态成熟，Pandas 是流水分析的事实标准 |
| 数据规矩 | Pydantic V2 | 类型安全 + 运行时验证，适合调查结论的强约束表达 |
| 数据结构 | pandas.DataFrame | 流水数据天然表格化，聚合查询效率高 |
| 输出格式 | Excel / Word | 调查工作流的实际交付物格式 |
| 无外部服务 | 纯本地 | 数据不出本地，符合纪律审查数据安全要求 |

### 3.3 设计意图分析（反常识根因）

> **反常识根因**：在常规数据产品里，「分析能力越强越好」是默认假设；但在 DataDone 的场景里，**「能说清楚为什么可疑」比「发现更多可疑点」更重要**。
>
> 规则引擎给出的每一个结论（异常、模式、风险分）都可以精确回溯到原始流水行、阈值配置、计算公式。这种「可审计性」是调查场景的核心需求。如果引入 AI 后直接让模型读原始流水并给出「我觉得可疑」的结论，即使准确率很高，也会破坏证据链的可解释性。
>
> 因此，AI 在该系统中的正确角色不是「替代规则发现异常」，而是「在规则已标定的异常上，生成更易理解的叙事与假设」。

## 四、本质反推

### 4.1 本质定义

DataDone-RE 的本质是：

> **在「仅有四类本地数据、无外部参照」的强约束下，建立「以自我历史为基准」的相对坐标系，把多源流水数据转化为可审计、可回溯、可解释的调查线索信号。**

### 4.2 本质检验

| 现有属性/方法 | 能否由本质定义解释 | 说明 |
|---|---|---|
| 四类数据加载器 | ✅ | 输入约束直接决定了数据源的边界 |
| 行为基线模块 | ✅ | 「自我历史为基准」的核心实现 |
| 异常检测（σ 偏离） | ✅ | 相对坐标系下的偏离度量 |
| 行为模式识别 | ✅ | 异常不是孤立的，组合后形成线索信号 |
| 时序链分析 | ✅ | 多源信号交叉验证，增强可解释性 |
| 风险研判评分 | ✅ | 把多个信号综合为调查优先级 |
| Pydantic 数据模型 | ✅ | 可审计、可回溯的结构保障 |
| Excel + Word 输出 | ✅ | 线索信号的两种消费形态 |
| 无 LLM 运行时 | ✅ | 黑箱结论与「可解释性」本质冲突 |

**结论**：本质定义通过检验，可以锚定后续所有设计决策。

### 4.3 类归属

由本质定义确定，DataDone-RE 属于 **「证据信号生产系统」**（而非「通用 BI 工具」或「AI 风控系统」）。

### 4.4 系统边界

- ✅ 做：在四类数据内发现相对异常、识别行为模式、构建时序证据链、生成可审计报告。
- ❌ 不做：联网查询、外部知识推理、自然语言直接指控、不可解释的「智能评分」。

### 4.5 本质洞察（一句话点破）

> **DataDone 不是「发现异常」，而是「在数据沙漠里建立相对坐标系，把异常标在地图上」。**

## 五、改进建议（引入 AI 的切入点）

基于以上反推，AI 能力的引入应遵循以下原则：

1. **AI 不替代规则信号**：LLM 只能消费 `AnalysisResult` 等结构化输出，不能直接读原始流水做无约束判断。
2. **AI 输出必须可溯源**：每个 AI 生成的叙事、假设、建议都必须绑定到具体的异常 ID、模式 ID、时序链 ID。
3. **AI 失败可降级**：当 LLM 不可用时，系统必须能回到现有规则报告，不阻塞核心流程。
4. **AI 是「翻译层」而非「发现层」**：把规则引擎的「信号语言」翻译成调查员的「自然语言」，降低理解成本。
