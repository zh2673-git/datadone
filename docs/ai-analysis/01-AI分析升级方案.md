# DataDone-RE AI 分析升级方案

> 本文档按「本质工坊」场景 C（项目开发）的输出层结构组织：项目目标 → 本质定义 → 架构总览 → 模块递归 → 验证方式 → 项目愿景。
> 思考层已走完三阶合一（是什么 / 为什么 / 怎么做），顿悟触发点按体裁融入对应章节。

## 一、项目目标

### 1.1 背景

DataDone-RE 已完成基于规则的多源数据分析流水线，能够稳定产出 Excel 详表与 Word 解读报告。随着数据量增加和调查场景复杂化，现有报告存在以下可读性瓶颈：

- 异常、模式、时序链、风险评分等信息分散在多个工作表，调查员需要跨表阅读才能形成完整判断。
- Word 报告虽然做了聚合解读，但模板化较强，难以针对具体个案生成灵活的调查假设。
- 调查员无法对系统「提问」，例如「张三和李某之间有哪些可疑往来？」需要手动检索多个表格。

### 1.2 目标

在不破坏现有规则分析流水线的前提下，引入 AI 协同层，实现：

1. **智能叙事**：基于规则分析结果自动生成案件级、人员级、线索级的自然语言解读。
2. **调查假设生成**：把异常、模式、时序链组合成可验证的调查假设，并标注证据来源。
3. **交互式问答**：允许调查员用自然语言询问已分析数据，系统基于结构化结果回答。
4. **报告增强**：把 AI 生成的叙事与假设无缝融入现有 Word / Excel 报告。
5. **安全可控**：AI 输出必须可溯源、可校验、失败可降级。

### 1.3 一句话点破（顿悟触发①）

> **AI 分析不是让系统「更聪明地找异常」，而是让系统「会把异常讲成调查员能听懂、能质疑、能行动的故事」。**

## 二、本质定义

### 2.1 升级后的系统本质

> **AI 升级后的 DataDone 是一个「证据信号 + 叙事翻译」双轮驱动的调查辅助系统：规则引擎负责生产可审计的证据信号，AI 协同层负责把信号翻译为可理解、可追问、可校验的调查叙事与假设。**

### 2.2 本质检验

| 新属性/方法 | 能否由本质定义解释 | 说明 |
|---|---|---|
| LLM 接入层 | ✅ | 为叙事翻译提供语言能力 |
| 符号校验层 | ✅ | 确保 AI 输出不偏离规则信号 |
| AI 分析引擎 | ✅ | 信号 → 叙事 / 假设的核心翻译器 |
| AI 报告生成器 | ✅ | 把叙事注入现有报告格式 |
| 交互式问答 | ✅ | 叙事能力的反向查询形态 |
| 失败降级 | ✅ | 翻译层失效时，证据信号层仍可独立工作 |
| 事实溯源 | ✅ | 每个叙事都必须能回溯到规则信号 |
| 不直接分析原始流水 | ✅ | 避免黑箱结论，保护证据链可审计性 |

**结论**：升级后的本质定义通过检验。

### 2.3 类归属

由本质定义确定，升级后的系统属于 **「可审计的 AI 辅助调查叙事系统」**（在原有「证据信号生产系统」基础上增加叙事翻译能力）。

### 2.4 系统边界（区分属性）

- ✅ 做：
  - 基于 `AnalysisResult` 生成自然语言叙事。
  - 基于规则信号生成调查假设。
  - 基于规则信号回答自然语言问题。
  - 把 AI 结论以结构化形式注入报告。
  - 对 AI 输出做符号校验与事实溯源。
  - LLM 不可用时降级到规则报告。

- ❌ 不做：
  - 让 LLM 直接读取原始流水并自主判定异常。
  - 让 LLM 生成无法溯源到规则信号的「新发现」。
  - 让 LLM 替代规则引擎做评分、排名、证据链判断。
  - 把原始数据发送到外部不可控服务。
  - 生成确定性法律结论（如「构成受贿」）。

## 三、架构总览

### 3.1 升级后整体架构

在现有四层架构之上，新增 **AI 协同层**。该层位于「分析引擎」与「导出引擎」之间，只消费 `AnalysisResult`，不触碰原始数据。

```
┌─────────────────────────────────────────────────────────────┐
│                       接口层（CLI / API）                    │
├─────────────────────────────────────────────────────────────┤
│  数据加载层  │  银行 / 微信 / 支付宝 / 话单 Loader            │
├─────────────────────────────────────────────────────────────┤
│  分析引擎层  │  11 步规则分析器 → AnalysisResult             │
├─────────────────────────────────────────────────────────────┤
│  AI 协同层   │  LLM 接入 → 符号校验 → AI 分析 → 报告增强      │
│              │  （新增模块，见下方展开）                       │
├─────────────────────────────────────────────────────────────┤
│  导出引擎层  │  Excel 导出 / Word 导出                        │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 AI 协同层内部结构

```
AI 协同层
├── LLM 接入层（LLM Provider Layer）
│   ├── Provider 抽象：OpenAI / Ollama / 本地模型统一接口
│   ├── 模型路由：复杂叙事用强模型，简单校验用轻量模型
│   └── 上下文管理：Token 预算、会话隔离、结果缓存
│
├── 符号校验层（Symbolic Validation Layer）
│   ├── 输入 Schema：只允许消费 AnalysisResult 中的指定字段
│   ├── 输出 Schema：强制 AI 输出结构化 JSON
│   ├── 事实溯源：每条 AI 结论必须绑定 evidence_refs
│   └── 幻觉检测：检查 AI 输出是否超出输入信号范围
│
├── AI 分析引擎（AI Analysis Engine）
│   ├── 叙事生成器（Narrative Engine）
│   ├── 假设生成器（Hypothesis Engine）
│   └── 问答引擎（Q&A Engine）
│
├── AI 报告生成器（AI Report Builder）
│   ├── Word 叙事段落注入
│   ├── Excel AI 摘要工作表
│   └── 证据来源脚注
│
└── 失败降级层（Fallback Layer）
    ├── LLM 不可用检测
    ├── 规则报告兜底
    └── 人工确认标记
```

## 四、模块递归

### 4.1 顶层模块划分

| 模块名 | 职责 | 与本质的关系 |
|---|---|---|
| `ai.llm_provider` | 统一封装多种 LLM 后端 | 叙事翻译的语言能力基座 |
| `ai.prompt_manager` | 版本化管理 Prompt 模板 | 保证叙事风格与约束可复制 |
| `ai.symbolic_validator` | 输入/输出校验、事实溯源、幻觉检测 | 保护证据链可审计性 |
| `ai.narrative_engine` | 生成案件/人员/线索级叙事 | 信号 → 故事的核心翻译 |
| `ai.hypothesis_engine` | 生成可验证的调查假设 | 把信号组合为行动指引 |
| `ai.qa_engine` | 自然语言问答 | 叙事能力的交互式调用 |
| `ai.ai_report_builder` | 把 AI 产物注入报告 | 叙事能力的交付形态 |
| `ai.fallback_manager` | 失败检测与降级 | 保证信号层独立可用 |

### 4.2 关键模块状态与接口（摘要）

#### LLM 接入层

- 内部状态：`provider_config`, `model_mapping`, `cache`
- 对外接口：`generate(prompt, schema, context) → validated_json`

#### 符号校验层

- 内部状态：`input_schema`, `output_schema`, `evidence_rules`
- 对外接口：`validate(input_data, ai_output) → ValidationResult`

#### AI 分析引擎

- 内部状态：`analysis_result_snapshot`, `generated_insights`
- 对外接口：
  - `generate_narrative(scope, person=None) → NarrativeResult`
  - `generate_hypotheses(person) → list[Hypothesis]`
  - `answer_question(question, person=None) → QAResult`

#### AI 报告生成器

- 内部状态：`report_template`, `ai_insights`
- 对外接口：`enrich(report_data, ai_insights) → EnrichedReportData`

### 4.3 类-属性-方法-路由（由本质锚定）

由本质定义「信号 → 叙事」推导：

- **类**：`AISystem`（信号翻译系统）
- **属性**：
  - `llm_provider`：语言能力
  - `symbolic_validator`：可审计约束
  - `narrative_engine`：叙事翻译能力
  - `hypothesis_engine`：假设生成能力
  - `qa_engine`：交互能力
  - `report_builder`：交付能力
  - `fallback_manager`：安全边界
- **方法**：
  - `translate_signals()`：信号 → 叙事（本质在动作中的体现）
  - `generate_hypotheses()`：信号 → 假设
  - `answer()`：自然语言 → 结构化信号 → 自然语言
  - `enrich_report()`：叙事 → 报告
  - `validate()`：校验叙事不偏离信号
  - `fallback()`：失效时回到规则输出
- **路由**：
  - 单人模式：为每个人生成独立叙事与假设。
  - 合并模式：为多人交叉关系生成综合叙事。
  - 问答模式：根据用户问题动态选择信号子集。
  - 离线模式：LLM 不可用时跳过 AI 层。

任意属性/方法/路由如果无法回溯到「信号 → 叙事」这一本质，即为冗余或错位。

## 五、验证方式

### 5.1 前置条件 P

- `AnalysisResult` 已成功生成且包含至少一个非空分析维度（异常、模式、时序链、风险）。
- LLM Provider 配置合法（API Key 或本地模型路径至少一个可用）。
- Prompt 模板版本与代码版本匹配。

### 5.2 后置条件 Q

- AI 生成的每条叙事/假设都有 `evidence_refs` 字段，可回溯到 `AnalysisResult` 中的具体条目。
- AI 输出经过符号校验，不存在与输入信号矛盾的结论。
- AI 输出为结构化 JSON，可被报告生成器消费。
- 当 LLM 不可用时，系统能输出不含 AI 内容的规则报告。

### 5.3 不变量 I

- **信号优先不变量**：AI 不能生成规则引擎未发现的「新异常」。
- **可审计不变量**：每个 AI 结论必须能被人工复核其证据来源。
- **安全不变量**：原始流水数据不离开本地，LLM 只消费脱敏后的结构化信号。
- **兼容不变量**：不引入 AI 时，现有规则分析流水线行为保持不变。

### 5.4 关键验证指标

| 指标 | 目标值 | 说明 |
|---|---|---|
| AI 输出可解析率 | ≥ 98% | 输出 JSON 必须符合 schema |
| 事实溯源覆盖率 | 100% | 每条结论都有 evidence_refs |
| 幻觉检出率 | ≥ 95% | 符号校验能发现大部分虚构结论 |
| 降级成功率 | 100% | LLM 失败时规则报告必须可用 |
| 报告兼容性 | 100% | 新旧报告在下游消费端无差异 |

## 六、项目愿景

### 6.1 视角升级（顿悟触发③）

> 阶段 1 我们说「AI 是把异常讲成故事」。升级完成后，视角应当再提升一层——
>
> 真正的本质不是「给数据分析系统加一个 AI 叙事模块」，而是**在调查工作流中建立一个「人机协作的证据解释协议」**：规则系统负责「发现信号」并保证可审计，AI 负责「解释信号」并降低理解成本，调查员负责「质疑信号」并决定行动。
>
> 这意味着：判断一个 AI 分析功能是否成功，不是看它生成了多少文字，而是看它**是否让调查员更快、更准地找到需要追问的那个点**。

### 6.2 重新定义的问题

> 不是「如何用 AI 发现更多异常」，而是「如何让 AI 在保持证据链可审计的前提下，把已发现的异常转化为可行动的调查叙事」。
>
> 下次设计类似系统时，先问「规则信号在哪里」，再问「AI 如何翻译这些信号」，而不是让 AI 直接面对原始数据讲故事。
