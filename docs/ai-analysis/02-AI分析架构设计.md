## 二、技术选型

### 2.1 技术栈决策

| 决策项 | 选择 | 推导逻辑（回溯本质） |
|---|---|---|
| LLM 协议 | OpenAI-compatible API | 可兼容 OpenAI / Azure / 本地 vLLM / Ollama，便于在本地与云端之间切换，保护数据安全 |
| 本地模型运行时 | Ollama / vLLM | 数据敏感场景下，优先本地运行；vLLM 适合高并发，Ollama 适合快速验证 |
| 模型路由 | 强模型（如 Qwen-72B / DeepSeek-V2）用于叙事生成；轻量模型（如 Qwen-7B）用于校验 | 平衡成本与效果；复杂叙事需要强模型，格式校验可用轻量模型 |
| Prompt 管理 | 文件化 Jinja2 模板 + 版本号 | 便于追踪、回退、A/B 测试；与代码版本解耦 |
| 输出格式 | JSON Schema | 符号校验层的基础；强制结构化输出 |
| 校验框架 | Pydantic + 自定义规则引擎 | 复用现有数据规矩能力，保持一致性 |
| 缓存 | 本地 JSONL / SQLite | 相同输入避免重复调用 LLM，降低成本并提升稳定性 |
| 依赖注入 | 与现有 Application 类一致 | 保持架构风格统一 |

### 2.2 为什么不选择某些技术

| 未选择 | 原因 |
|---|---|
| 让 LLM 直接读取原始 DataFrame | 破坏可审计性，易产生黑箱结论 |
| 使用 LangChain / LlamaIndex 等重框架 | 当前需求明确（结构化输入 → 结构化输出），重框架增加复杂度且无必要 |
| 云端闭源大模型作为默认 | 数据安全与合规风险高，仅作为可选 Provider |
| 向量数据库 | 当前场景是结构化信号查询，不需要语义检索 |

## 三、设计依据

### 3.1 反常识根因（设计层顿悟触发）

> **反常识根因**：业界常见的 AI 数据分析方案是让大模型直接「看」原始数据并给出结论，但在调查场景里，**「AI 不直接看原始数据」反而比「AI 直接看原始数据」更有价值**。
>
> 原因在于：调查结论必须经得起复核。如果 AI 直接读流水并输出「张三受贿」，调查员无法快速判断这是模型幻觉还是真实信号；但如果 AI 只读规则引擎已标定的信号，并输出「张三在春节收到李某 52000 元，与该时段通话记录形成时序链（证据链 ID: TL-003）」，调查员可以直接点开原始流水验证。
>
> 因此，架构上把 LLM 放在 `AnalysisResult` 之后，不是能力降级，而是**把 AI 的创造力约束在可审计的边界内**。

### 3.2 架构设计原则

1. **信号优先原则**：AI 只能消费规则引擎输出的结构化信号，不能绕过规则引擎。
2. **可溯源原则**：每条 AI 结论必须携带 `evidence_refs`，指向 `AnalysisResult` 中的具体条目。
3. **校验前置原则**：AI 输出在进入报告前必须经过符号校验。
4. **失败隔离原则**：AI 层失败不影响规则分析流水线。
5. **渐进增强原则**：AI 功能是可选开关，默认关闭，旧行为不变。

### 3.3 与现有架构的融合点

| 现有模块 | AI 层融合方式 |
|---|---|
| `Application` | 新增 `ai_enabled` 开关，在 `analyze()` 之后可选调用 `ai_analysis.analyze()` |
| `AnalysisResult` | 新增 `ai_insights` 字段，承载 AI 产物 |
| `ReportBuilder` | 新增 `enrich_with_ai()` 方法，把 `ai_insights` 注入 `ReportData` |
| `WordExporter` | 在「重点发现」「风险研判」等章节后增加「AI 调查叙事」小节 |
| `ExcelExporter` | 新增「AI 摘要」工作表，列出关键叙事与假设 |
| `CLI` | 增加「启用 AI 分析」选项与「AI 问答」子菜单 |

## 四、关键设计决策记录

### 4.1 决策：LLM 输入范围限定为 AnalysisResult

- **方案 A**：让 LLM 读取原始流水 DataFrame。
- **方案 B**：让 LLM 只读取 `AnalysisResult`。
- **选择 B**。理由：保证可审计性；原始流水数据量大，直接输入会超出上下文窗口；规则信号已经把关键信息压缩好。

### 4.2 决策：AI 输出必须是结构化 JSON

- 所有 Prompt 末尾附加统一指令：「请严格按以下 JSON Schema 输出，不要包含任何解释性文字。」
- 输出 schema 由 `symbolic_validator` 定义，不同任务（叙事/假设/问答）使用不同 schema。

### 4.3 决策：模型路由策略

- 叙事生成 → 强模型（需要理解复杂上下文、生成连贯文本）。
- 假设生成 → 强模型（需要跨信号推理）。
- 问答 → 中等模型（在已生成的叙事中检索/综合）。
- 格式校验 / 幻觉检测 → 轻量模型或规则引擎（成本低、速度快）。

### 4.4 决策：失败降级策略

| 失败场景 | 处理动作 |
|---|---|
| LLM Provider 不可达 | 跳过 AI 层，输出规则报告，日志标记 `ai_skipped` |
| AI 输出无法解析 | 尝试重试 1 次；仍失败则丢弃该条 AI 结论，保留其他结论 |
| AI 输出未通过符号校验 | 标记为 `unvalidated`，不进入正式报告，仅保留在调试日志 |
| AI 输出与规则信号矛盾 | 以规则信号为准，AI 结论降级为「待复核建议」 |
| 单个模块失败 | 不影响其他 AI 模块继续执行 |

## 五、非功能性设计

### 5.1 性能

- AI 调用是 I/O 密集型，使用异步或线程池并发处理不同人员的叙事生成。
- 启用本地缓存，相同 `AnalysisResult` 哈希直接返回缓存结果。

### 5.2 安全

- 默认优先使用本地模型。
- 若使用云端模型，必须配置脱敏中间层：只发送结构化信号，不发送姓名、账号等原始敏感字段（或配置化决定是否脱敏）。
- 所有 AI 调用记录写入审计日志。

### 5.3 可维护性

- Prompt 模板与代码分离，支持热更新。
- AI 模块遵循现有四层设计（数据规矩 → 存储 → 流转 → 接口）。
- 每个 AI 子模块都有独立的单元测试与 Mock Provider。
